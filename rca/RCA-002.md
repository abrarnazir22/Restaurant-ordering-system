# RCA-002: Chronological Validation Failure in Table Reservations (5-Why Analysis)

**Incident / Defect:** Table reservations accepted for past dates and past times.  
**Severity:** P0 (Blocker)  
**Impact:** Ghost bookings created in the database for expired time slots, skewing restaurant table availability and staff scheduling.  
**Author:** Lead Systems Architect & Quality Engineer  

---

## 1. Incident Overview
Customers could submit reservation requests for yesterday's date or past hours today, which were saved to the database as valid pending reservations.

---

## 2. 5-Why Root Cause Analysis

1. **Why were past-date reservations accepted by the system?**  
   Because the reservation API returned HTTP 201 Created and persisted the record in MongoDB.

2. **Why did the API return HTTP 201 Created for a past date?**  
   Because `POST /api/reservations` lacked server-side date-time comparison logic.

3. **Why was date-time validation absent on the server?**  
   Because developers assumed frontend HTML `<input type="date">` attributes were sufficient to restrict date selection.

4. **Why was client-side validation bypassed?**  
   Because clients could send arbitrary date strings directly via API requests or script execution, bypassing the HTML UI.

5. **Why was server-side chronological defense not implemented originally?**  
   Because the development lifecycle followed an "optimistic client" model rather than a "zero-trust backend validation" architecture.

---

## 3. Corrective & Preventive Actions (CAPA)

- **Immediate Fix:** Created centralized `validateFutureDateTime(date, time)` enforcing `targetDate >= (Date.now() + 15 mins)` and integrated it into `src/Routes/reservations.js`.
- **Automated Verification:** Added Playwright tests `RES-02` (past date) and `RES-03` (past time on today's date) in `tests/e2e/reservations.spec.js`.
- **Architecture Standard:** Mandated zero-trust server-side validation for all state-changing endpoints.
